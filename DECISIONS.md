## Catalog Customization (Configuration screen) — 2026-09-06

Full write-up lives in `.claude/agents/full-stack-engineer.md`'s "Catalog Customization" section (tables, DB schema, migration list). This entry is the short version of the decisions that shaped it, for anyone skimming before diving into the code.

**Soft-disable-only deletes, everywhere.** Removing a tile, card, sub, or third-level option in the Configuration screen never issues a hard `DELETE` for any row that has ever reached the server — it flips `is_active = false` (`set_catalog_category_active`/`set_activity_active`, both `SECURITY DEFINER` — see below for why). This preserves `scheduled_activities`/`activity_events` FK integrity and matches rule 11's spirit (recoverable, not gone). The ONE exception: a row added and then removed again in the SAME still-unsaved Configuration session, before Save — it never reached the server, so there is nothing to soft-delete; the client just drops it from the staged working set (`configReducer.ts`'s `isTempId` check).

**No cascade on deactivation.** Deactivating a tile does NOT cascade to soft-disable its own cards/subs/thirds in the database, and deactivating a card does not cascade to its subs. A single `UPDATE` on exactly the row the user removed is enough: `buildSnapshotFromRows` (`domain/catalog.ts`) already makes a card whose `category_id` no longer names an ACTIVE category unreachable from the effective catalog, regardless of the card's own `is_active` value — its whole subtree simply never gets visited when the tree is collapsed into tiles → cards. This keeps the RPC surface narrow (one row touched per call) and the client's optimistic state trivially consistent with it.

**Attribute-option overrides are scoped per ACTIVITY (the top-level card), never per tile.** Two cards in the same tile (e.g. "Night Sleep" and "Supplements", both under Sleep & Rest) can restrict Activity Quality/Chronic Symptom/Protective Response completely differently. No rows for an `(activity_id, attribute_type)` pair means "show the full master list" — the default for all 53 pre-existing items, zero migration risk. The master vocabularies (`QUALITIES`/`SYMPTOMS`/`FLAGS`, `data/activities.ts`) stay fixed TS constants; the database never mirrors them — only the allow-list (plain `text`, not FK'd) lives there, so there is no second copy of the vocabulary to keep in sync.

**No reorder in v1.** New tiles/cards/subs/thirds simply append (`sort_order` = current max + 1 within the sibling group). Drag-reorder is out of scope — not stubbed, not half-built behind a flag, just not present. `sort_order` still exists on every row (backfilled from the pre-existing `data/activities.ts` array order for all system rows) so a future reorder feature has something to write to.

**`SECURITY DEFINER` is used for exactly two functions, both narrow.** `set_catalog_category_active`/`set_activity_active` are the only catalog RPCs that bypass RLS's normal "own row" policies, and only to flip one boolean column. This is deliberate: this product has no multi-user support at all (confirmed in `PRODUCT-HANDOFF.md` — one owner), but a SYSTEM row (`created_by is null`, e.g. a stock tile) can never satisfy an "own row" update policy under any user's session, by design — nobody should ordinarily be able to mutate the shared system catalog directly. The Configuration screen's whole premise, though, is that its one user CAN hide any tile/card, stock or their own. Rather than inventing a new RLS carve-out, these two functions get the same treatment this project already gives `encrypt_flags`/`decrypt_flags` and `internal.encrypt_note_entry_text` — a `SECURITY DEFINER` function scoped to exactly one narrow, auth-gated operation, never a general bypass. Every OTHER catalog RPC (`create_catalog_category`, `create_catalog_activity`, `set_activity_attribute_options`, `get_effective_catalog`) stays `SECURITY INVOKER` (the default), relying on RLS as the real enforcement boundary, matching every existing RPC's convention in this codebase.

**Local-first catalog cache, same contract as the board.** `CatalogContext` loads instantly from a `localStorage` cache (`state/catalogLocalPersistence.ts`), falling back to the system default (`domain/catalog.ts#defaultCatalogSnapshot`, converted once from `data/activities.ts`) when nothing is cached yet — then reconciles against the server in the background. `data/activities.ts` itself is untouched and is now purely the default-seed module (and the source generators for the seed migrations read from) — no runtime render path imports it directly any more; everything reads through `CatalogContext`.

**Configuration screen edits are staged, not instant.** Unlike every other write in this app (rule 6 — instant local, background sync per action), the Configuration screen deliberately batches: nothing reaches `CatalogContext` or the server until Save/Store is pressed (`configReducer.ts` mirrors `boardReducer.ts`'s own staging pattern for this reason). Once Save is pressed, rule 6 resumes as normal — the merged result applies to `CatalogContext` (and therefore the Home screen) instantly, and the queued operations (`state/configSync.ts`) sync to the server in the background, in dependency order (a tile before the cards added under it), substituting each `create*` op's real id into any later op that still names its temporary one.
